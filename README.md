# Capacity Model (synthetic)

A 52-week workforce capacity-planning model for **Northbrook Records Services**,
a **fictional** six-site medical-records request operation. Written in Python.

**Live dashboard (synthetic data):** <https://capacityplanningmodel-sclent.streamlit.app/>

It runs the same model as this repository — the 21 saved runs it reads are the
ones committed in `app/data/`, and the build-your-own panel runs the model
itself — so every figure on screen is one the checks here cover.

Siri L. (GitHub: Sclentzie) is the architect: she designed the model and made
the modelling decisions recorded in the specification, which she drafted with
Claude as a planning partner, and reviewed every checkpoint.
[Claude Code](https://claude.com/claude-code) was the builder, working to that
specification one task at a time. The design document —
[docs/Capacity_Model_Spec.md](docs/Capacity_Model_Spec.md) — is the source of
truth for every input, formula, default and validation check, and records each
decision with its date.

## Everything here is synthetic

Every number in this repository is either an assumption typed into a YAML file
or data **generated by this code** from a fixed random seed. There is no real
company, patient or employee data in it, and none is ever fetched. Run it twice
and you get the same answers.

The operation is invented. The healthcare setting is a modelling scenario and
does not represent any real organization's process. Every default is an
**illustrative starting assumption, not an industry benchmark**.

## What it does

**Demand and forecast.** One driver — records requests per site per week — runs
through 156 weeks of generated history with trend, seasonality, holidays and
noise. Two forecasting methods are fitted and scored against each other on a
13-week holdout they never see: classical decomposition (seasonal index, linear
trend on the de-seasonalised series) and Holt-Winters as the challenger. The
model reports the error for both and uses the better one. Holidays are known
years ahead, so their effect is divided out before fitting and multiplied back
on by date.

**Workload.** Requests become work through 24 work types across five stages, each
measured per request or per chart — a bulk payer audit is ten charts, so it
multiplies retrieval without multiplying intake — and each carrying a lag that
places its hours in the week the work actually lands. Live work at the counter
and on the phones is solved with **Erlang C** at half-hour intervals against two
service goals (80% of calls in 20 seconds, 90% of walk-ins within 10 minutes),
with an 85% occupancy cap. Back-office work is a
**backlog**: each queue carries what the week before left, and is measured in days
of inventory against its stage goal and the 5-day overall goal.

**Supply.** A weekly ledger per role and site tracks starting headcount, hires,
attrition, the training curve, shrinkage and the productive hours that survive
it. Headcount stays fractional — attrition is a weekly rate applied to a
headcount, not a list of named leavers — and no person-level identifiers are
stored anywhere.

**Coverage and hiring.** Where a week is short, the model tries the cheapest
option first: borrow from a nearby site — the round trip comes off the lending
site's hours and the mileage is charged at the set rate — then authorise
overtime against a cap, then accept the gap. Each of those is written to an
event log with
the fields a real coverage log would carry, including a suggested cause for a
person to confirm. A role that stays more than 1 FTE short for three
consecutive weeks triggers a hiring class, sized to the gap and rounded up to
whole people, with a hire-by date counted back through requisition, onboarding
and ramp.

**Automation and human-in-the-loop.** Two halves, kept separate because they
behave differently. *Deflection* removes contacts before they arrive, which
leaves a harder mix behind — calculated, not assumed. *Automation* lets a
machine do work that still arrives, and the work comes back: exceptions, a QA
sample, and legal sign-off where the law requires a person. The human cost a
machine displaces is priced on the **easy items it actually takes**, not an
average item, and the machine's own invoice — per-item fee, setup spread over a
year, one shared platform fee — is counted alongside the labor it saves.

**Scenarios.** 21 runs sit side by side: volume and attrition shocks, pooled
phones, service-goal changes, scheduling shapes, five automation variants, a
central records archive, coordinated digitization, and combinations. No scenario
re-tunes its roster, so each one reports what the change costs the operation it
actually has.

**One doorway in.** The model sits behind a single inputs-in, results-out
function — `capacity_model.api.run(overrides)` — which takes the same keys a
scenario file uses and refuses any key the inputs do not carry, so a typo fails
loudly instead of handing back the baseline. The workbook and the dashboard
both read their figures through it, built by the same table functions, so the
two cannot disagree about a number.

**The workbook.** One Excel file a leader can open without Python, with the ten
tabs the specification names: a curated Summary, all 21 scenarios, the plan and
the supply ledger week by week, the automation ranking, the coverage log, the
non-digital tracker, the hiring plan, the forecast scoreboard with its chart,
and every input used for the run with the YAML key that sets it. The model
writes the measures as values, so they tie to the cent; Excel computes the
totals and the differences as live formulas, so nothing is calculated twice in
two languages.

## Run it (Windows, PowerShell)

```powershell
py -3.14 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
$env:PYTHONPATH = "src"

# All 21 scenarios, the forecast chart, and the workbook (about eight minutes)
.venv\Scripts\python -m capacity_model.export
```

That one command writes `outputs/capacity_model_workbook_SYNTHETIC.xlsx` with
all ten tabs filled, chart included: the Forecast tab draws its own chart when
`outputs/` does not already hold one, which on a fresh clone it does not,
because generated files are not committed. Every stage can also be run alone
— `generate_data`, `forecast`, `work_volume`, `intervals`, `backlog`, `plan`,
`scenarios` — each writing its own CSVs and charts.

Library versions are pinned exactly in `requirements.txt`. A fixed seed only
reproduces the same answers on the same arithmetic, so the versions the checks
were run on are part of the model, not an installation detail.

### Run the dashboard

```powershell
.venv\Scripts\python -m streamlit run app/dashboard.py
```

It opens in a browser and reads the saved results in
`app/data/scenario_results_SYNTHETIC.json.gz` — all 21 runs, so the page loads
in under a second instead of waiting out the model.

Every view opens with three lines above the picker: what this is (a capacity
model of a fictional six-site records operation, on synthetic data), the
headline finding, and how to use the page. The figures in that finding are read
from the saved results rather than written into the page, so the headline
cannot go stale while the page still prints it — and a test checks them against
both the saved summary rows and the workbook's approved sentence for that run.

There are three views. **One run**: pick a run in the sidebar — the baseline
first, then the eight the Summary tab headlines, then the rest — and filter to
the network, a cluster or a site, and to the roles inside it. The page shows the
six headline measures against the baseline, that run's one-line finding where
the Summary has one, the weekly shortfall against the baseline, the all-in cost
split into labor and machine, and the Capacity Plan rows behind all of it, with
two downloads. **Compare all scenarios**: every run at once, ranked by what it
does to the all-in cost, with the same two downloads. **Build your own**:
assemble a run of your own and put it through the model on demand.

The build-your-own panel has a control for every lever the 21 scenario files
pull, grouped as Demand, Supply, Service, Structure, AI and automation, and
Timing, with each input's baseline value on its label. The AI and automation
group also shows each control's **spec 7.1 default** beside the baseline and
has a button that loads all thirteen of them at once — read from
`scenarios/ai_and_automation.yaml`, so the button loads the programme the
spec's own AI run reports rather than a copy of its numbers. Work types are
picked by their plain names, with the codes on the control's tooltip. A lunch
or break window that closes before it opens, falls outside the sites' opening
hours, or is not a whole number of the model's half-hour intervals is refused
in plain words before anything runs.

An **Advanced** box searches everything else in `assumptions.yaml` by key or by
the comment the file carries above it, and changes it through the same
validator a scenario file goes through — an input that does not exist is
refused before the run starts, and a combination the model rejects (two rates
over 100%, say) comes back with the model's own sentence. Because a text box
has no ends where a slider has them, the box also holds a value to the kind of
number its name says it is: a share or a rate between 0% and 100%, hours,
counts and costs not negative, a multiplier not negative either (zero is
allowed: on an attrition multiplier it means nobody leaves). These are rules about
kinds, not bounds on each input — nothing is added to the YAML. A value more
than three times its baseline, or under a third of it, is allowed and warned
about in yellow: outside the range this model was tested in.

Nothing runs until you press **Run**. Streamlit reruns the script on every
widget change, and a panel that ran the model on each of those would spend
twenty-five seconds answering a question you had not finished asking. Inputs
already run come back at once, because the runs are remembered by a signature
of the overrides. **Reset to baseline** puts every control back and forgets
them.

A custom run is called **Custom run (synthetic)** however faithfully it copies
a scenario, and both its downloads carry the inputs that were changed — the
Excel file in an INPUTS CHANGED section above the table, the CSV on comment
lines above the header row. A custom run's inputs exist nowhere else, so a file
without them would be unreadable a week later. Its results are shown through
the same cards, charts and table as a saved run, so the two cannot be reported
differently. A test sets the controls to five scenario files' inputs and
checks the figures come back as those scenarios', to the cent.

**One name, one format, one explanation per measure.** A measure is written the
same way wherever it appears — dollars whole, FTE to two decimals, hours to one,
days to two — from one table of formats shared by the cards, both tables and the
chart axes, and it is called what the workbook calls it. Each measure also has
one plain-language sentence saying what it is, and that same sentence is the
hover on the card and on the comparison table's column header. Every filter,
control and button on the page carries help text too, which a test checks by
walking the real page rather than by listing them.

**Two themes, and the colours that mean something.**
`.streamlit/config.toml` is committed, so the hosted app is themed by the same
file a local run is, and it carries two full palettes as `[theme.light]` and
`[theme.dark]`. Light is a warm cream page (`#faf7f2`, never pure white — white
is the one background that makes a table of figures look like a spreadsheet), a
step darker for the sidebar (`#f1ebe0`), dark charcoal text (`#24262b`) and a
teal accent (`#3a7a8c`) on the sliders, buttons and focus outlines. Dark is a
deep charcoal page (`#191b1e`, never pure black), a step *lighter* for the
sidebar (`#232629`), warm off-white text (`#edeae4`) and the same teal made more
vivid (`#107e9c`). A viewer switches in the menu at the top right of the page,
where Streamlit draws a System / Light / Dark control — and draws it *only*
because both palettes exist; ship one custom theme and the control is hidden.
System is the default, so a reader on a dark-mode machine lands in dark mode
unasked. There is no on-page toggle because Streamlit 1.67 has no API for
setting the theme from page code (`st.context.theme` is read-only), so the
sidebar points at the real control instead of faking one.

Nothing on the page picks its own shade any more. Switching Light/Dark in
Streamlit's menu re-themes the browser **without rerunning the script**, so a
colour this code chose from the mode was right when it was chosen and wrong the
moment the reader switched — a dark green left on a charcoal page at 1.4:1,
which is no colour at all, with nothing raising and nothing to notice until the
next rerun. Everything coloured here is therefore built so that it has no mode
to get wrong, by one of three mechanisms. A card's difference and a run's kind
in the sidebar are sent as a colour *name* and Streamlit resolves it in the
browser on every repaint. The workbook's scope and kind fills are translucent
washes, mixed down onto the cream page because a spreadsheet has no
transparency. And everything this page draws itself — the tables, the banners,
the download buttons — goes out as a CSS `light-dark(light, dark)` **pair**, so
both shades reach the browser and the browser picks. Red, green and blue stay
reserved for the cards — better, worse, no change — so nothing else uses them.

The **Scope** and **Kind** columns are coloured bold words (outside reviewers,
24 November). A word needs a text colour, and one text colour cannot serve both
pages: readable text needs 4.5:1, which caps a colour at about 0.17 relative
luminance on the cream page and demands at least 0.20 on the charcoal one, so
there is no single hex in between. `light-dark()` resolves that, because
Streamlit sets `color-scheme` on the app element and flips it on a menu switch
with no rerun — measured in a real browser, not assumed. The scope hues are the
ones the workbook already tints a scope cell with: amber for the North cluster,
violet for the South, slate for the back office. One line under the table says
what the three words mean, in the same three colours, and it replaced the two
keys with swatches that used to explain a colour that no longer exists.

The light-mode shades were **softened** on 25 November, because the in-house
testers found them loud on a cream page: the hue angle of each is held exactly
where it was, and the search walked saturation down and lightness up — a 23%
cut in saturation — which is as far as the three can soften together. The bar
that stopped it was not contrast but distinctness: desaturating pulls every hue
toward the same neutral, and the closest pair was only 44.8 apart to begin
with. The words now read at 5.1:1, 5.3:1 and 5.1:1 on the cream page, 42.6
apart at the closest, and dark mode is untouched (9.5, 6.8 and 8.2, 48.0
apart). The **panels** keep the saturated end of the same three hues, and that
split is measured rather than stylistic: a panel carries its hue at 12% and
then writes in that hue on top of the wash, and the softened amber reads at
4.37:1 on its own amber — under AA — at every alpha strong enough to see the
wash at all.

Those tables are therefore the page's own HTML rather than `st.dataframe`,
because the grid paints its cells on a canvas where no CSS and no markdown can
reach. CSS gives back the sticky header, the scrolling body and a tooltip on
every column header; what it cannot give back is sorting by clicking a header,
so there is a **Sort by** control and a high-to-low toggle above each table.
Every figure is written by the same function the cards use, so one measure
reads the same wherever it appears.

The two downloads wear two of the scope hues — violet for the formatted Excel
file, slate for the raw CSV — as a translucent fill and a 2px edge, with the
label left in the page's own text colour. The two alphas were searched rather
than picked: violet at 48% and slate at 38% is the lightest pair where, in both
palettes, each fill sits at least 22 from its page by delta-E, the two fills
sit at least 22 from each other, and the label still clears AA on either. They
are not equally loud hues, so one shared strength left either slate invisible
or violet shouting. The **SYNTHETIC** banner is a 12% wash of the amber with
its lead word in the hue, rather than the filled warning block it was, which
read as "something is wrong here" when nothing is.

**Every notice on the page is drawn the same way** as of 25 November: a wash of
its hue, the sentence written in that hue, and a thin left edge — the design
the workbook's findings already used. Twelve of them were Streamlit's own
`st.info`, `st.warning` and `st.error` blocks, which in light mode are filled
panels in a palette that was never this page's; the testers named the last one
a reader meets ("Set the controls above and press Run") and it was true of all
twelve. The hue is the only thing that differs between them, and there are
three because a notice here is in one of three registers that are not
interchangeable: **blue** for something to know or to do next, **amber** for
something true and allowed and worth reading twice, **red** for a value the
model or the validator refused. A refusal drawn in the finding's calm blue
would be a worse light mode than the block it replaced. Each one is measured on
every surface it is drawn on, the sidebar included, where the wash sits over
the panel colour rather than the page: the worst sentence reads at 4.8:1. What
they gave up is Streamlit's Material icon beside each; a lead word in the
sentence — *Refused*, *Queued*, *Out of date* — says the same thing in
something a screen reader can also read. There is also **clear space** between
each table and the two download buttons under it, which sat flush against the
detail table at 1440 before this round: measured at zero. And picking
a different run scrolls the main column back to the top, because a run is a
whole page and a reader who was at week 40 of the table should not land in the
middle of the next one.

Both tables fit the page with no sideways scroll, at 1280, 1440 and 1920, with
the sidebar open and collapsed. That took short headers with the full workbook
name on hover — the comparison table's last column read "Requester turnaround,
mea…" at 1440 — and a fifth of a rem off each cell's padding, which is 108px
across the detail table's seventeen columns. Money is written with the sign in
front of the dollar: **-$51,569**, never `$-51,569`, which is not how anybody
writes money and reads, for a moment, as a dollar amount of minus something.
And the baseline's **Kind** says *Baseline*, in no colour: its file declares a
kind like every run, but on a table ranked against the baseline, calling the
baseline a choice reads as if somebody were proposing it.

Nothing here was eyeballed. Tests recompute every contrast ratio in both
palettes and hold each to WCAG AA — charcoal on cream is 14.2:1, off-white on
charcoal 14.4:1, a white label on either teal button 4.8:1 and 4.7:1 — and they
also hold the colours *apart*, by CIE delta-E, so that no two things which mean
different things can look the same. That second measure is what settled Siri's
question about the no-change blue against the teal accent, which is why the
accent is a teal that means nothing rather than a colour already spoken for.

Since the cards and the kinds stopped choosing their own shades, those checks
measure what Streamlit actually paints rather than what this project declares —
a distinction that turned out to matter, because Streamlit does not use the
configured hex for a colour name, it derives a more contrasty one from it. Our
`#5b3a8c` violet is painted `#382456`. The six rendered shades are recorded in
`views.RENDERED_COLOURS`, measured in a real browser, and
`tests/test_live_colours.py` drives the actual Light/Dark menu with no refresh
and re-measures them. On contrast the derivation is an improvement — the worst
of the six is 6.7:1 where the worst hand-picked hex was 5.6:1 — but measuring
what is painted rather than what is declared also found six pairs closer
together than this project's own rules allowed, which the declared hexes had
been hiding.

Four of those were one kind against another, and they were settled two ways.
A kind is never colour alone — every kind label is printed as its own word
beside its own colour — so those pairs answer to the "obviously another
colour" bar (20) rather than the "could not be confused" bar (40). Three
cleared it already. The fourth did not: Streamlit painted Choice `#e4d0f5`
and Sensitivity `#dadde1`, 19.3 apart, which in a sidebar that writes them one
above the other is one pale colour. The cause was hue. Streamlit's derivation
preserves a configured colour's hue exactly and flattens everything else, and
the gray's hue sat 49 degrees from the violet's. Re-hueing the dark gray from
a cool `#afb6bf` to a slate `#88bdbe` moved the pair to 26.2 — measured in a
browser, after trying a warm gray that cleared the violet and then collided
with the orange instead.

A fifth pair was the better green against the teal accent on cream, 29.8
apart, and the reason turned out to be the same shape: both were teal. Green
was the one colour here left to Streamlit's own, and on a cream page it
derived to `#0c5a44` — hue 167, chroma 29 against the red's 50 — which
measures as a green and reads as dark gray. Declaring `#37a53d` in the theme
file takes the rendered shade to `#246b27`, hue 140, and the pair to 52.6.
Contrast falls from 7.7 to 6.1 to one, still well past AA, and the three
verdicts now read 6.1, 6.7 and 6.9 rather than one of them shouting. Dark
mode keeps its mint green, so the two palettes no longer share that hue —
deliberately, since they are never on screen together.

One pair is still open: the no-change blue against the teal accent in dark
mode, 32.8, recorded as a deliberately failing test rather than written off.
A colour is a thing done to the screen; the CSV is the same bytes it always
was. **The workbook wears the same palette** as of 11/23: its header rows are
in white bold on the page's own **dark slate** (`#44586B`) at 7.4:1 — the back
office's hue, so the header row sits with the sand, the lilac and the violet in
the cells under it. It was the navy nothing on the page used, then the accent
teal at 4.8:1, which is the colour of every slider and focus ring on the
dashboard and was chosen in the first place because it means nothing: a
spreadsheet has no sliders, so there it meant nothing twice; a row's Scope cell carries its
region, and a run's name on Capacity Scenarios carries its kind, in the same
six colours — mixed down onto the cream page, because Excel has no transparency
and a spreadsheet is a light-mode document. A test composites each of the
page's washes and fails if the two ever drift. Columns are fitted to what they
hold, with the plan-year total measured too, so nothing renders as ####.

Each run declares what KIND it is, in its own scenario file: a **choice** is
something the operation could decide to do, a **risk** is something that could
happen to it that nobody is proposing, and a **sensitivity** varies one input of
another run to test whether its finding holds. The dashboard shows it beside
every run and the workbook names sensitivity runs in italics, both reading the
same declared field — a sensitivity read as a proposal is how a finding gets
quoted as something it never said. Each kind carries its own colour —
**violet** for a choice, **orange** for a risk, **gray** for a sensitivity — as
a coloured word beside every run in the sidebar, and as the same word in the
comparison table's Kind column, in the same shade: one colour reached two ways,
by Streamlit's markdown in the sidebar and by a CSS pair in the table.

Each headline card is read one way: **green** moved the way a planner wants,
**red** moved the other way, **blue** did not move at all. All six measures are
better lower, required FTE among them. A difference that rounds to nothing at
the precision the card shows says *no change* in words instead of printing a
zero under an arrow — a rounding artefact should not wear a verdict — and the
exact difference is on the card's hover, so nothing is hidden by being rounded.

Roles are called what people call them — "Records Specialist", "Tier 1" —
everywhere on the page and, since 11/23, everywhere in the workbook and the
Excel download too. The short names come from `skills.yaml` beside the full
ones, so nothing here invents an abbreviation of its own; hover the table's
Role column for the full name. The CSV is the one place that keeps the model's
own codes, because a downloaded row has to match a workbook row and a code is
what survives being joined to something else. A test reads every string on
every tab and fails on a role code, not just on the Role column: a code can
arrive in a sentence as easily as in a cell.

Both charts are **locked**: the shortfall chart spans the whole plan year,
every week of it, and each chart's vertical axis is fixed to a round number
above the tallest value in the current selection. Neither can be panned or
zoomed, because a chart scrolled out of scale by a stray trackpad gesture
cannot be put back without reloading the page. Hovering still reads a value
off a line.

Every label on both charts reads left to right. Vega-Lite rotates a bar
chart's category labels to vertical as soon as it decides they do not fit,
and it had: measured in the browser, the two run names under the cost chart
were drawn on their side *and* cut short by the 180px default label limit, so
the longer one read "Site shortfall N1, …" sideways. The angle is set
explicitly now, which turns that off for good. There is nothing to abbreviate
either — the chart only ever draws two bars, the baseline and the run being
looked at, so a band is about 440px wide at 1440 and the longest run name is
136px. The full name fits flat with three times the room it needs, and the
bar's tooltip carries it as well. Both legends read along the bottom rather
than stacked up the right-hand side, one line of text under the picture they
describe.

Moving the legend under the picture put it where a light-mode reader looks,
which turned up a colour nobody here had chosen: Streamlit's chart theme
paints axis and legend labels `#808495`, and on this page's cream that is
3.48:1, under the 4.5 AA asks and under the bar every other word on the page
is held to. Dark was never in doubt at 14.30:1. The light end is now
Streamlit's own gray at its own hue and saturation, darkened the smallest
number of steps that clears AA with a margin — 4.88:1, and ΔE 9.5 from the
colour it replaces, so it still reads as a muted label rather than as body
text promoted onto the axis. It goes out as a `light-dark()` pair like every
other colour this page draws.

The detail table's headers are shortened to fit the page without scrolling
sideways — hover one for the workbook's own name for that column and what it
means. The CSV download is not shortened: it keeps the full headers and the
full precision, because a downloaded row has to match a workbook row.

**Two downloads, and the formatted one is the main button.** Wherever the page
offers a table to take away, **Download Excel (formatted)** sits first and
**Download CSV (raw data)** beside it. The Excel file is exactly what is on
screen — the same rows, in the same order, under the same headers, for the run
and the filters showing — wearing the workbook's own styling, because it is
written by the exporter rather than by a second set of rules: Arial, the slate
header row, the same number formats, negatives in parentheses, a frozen header
with a filter on it, and the hours gap and the totals still live Excel
formulas. It says above the table which run it is and what was filtered out, so
somebody opening it cold cannot sum a filtered column believing it is the
network. The CSV is unchanged and does the other job: raw data at full
precision under the model's own role codes, for anyone joining it to something
else. A test ties every figure in the Excel file to the figure on screen, to
the cent.

Back-office roles are one network team rather than site staff, so a site or
cluster view says that in words instead of drawing them at zero: a role that
was never based at a site is not absent from it, and a zero would read as a
measurement. That file is the one
generated file this repository commits, because a hosted app cannot spend nine
minutes before it shows anything. Rebuild it after changing any input:

```powershell

```

## What the model found

These are the findings the Summary tab carries, unchanged:

- **A 15% volume rise is the biggest risk in the plan:** +$1.06M, and turnaround
  misses the 5-day goal in 27 weeks, as overtime and undone work absorb the
  rise.
- **Pooling the phones is the largest saving, and it fixes the counter:** one
  pooled phone queue cuts uncovered hours from 420 to 21, while both service
  levels stay above goal.
- **Answering 40 seconds slower saves only about 1 FTE,** because the blended
  counter-and-phone team is staffed to be available, not busy.
- **Automating only the two work types that pay back after setup fees saves
  about $14K,** less than one hiring class, so treat it as break-even. It saves
  hours while the remaining work gets less than about 3% harder; the dollars
  hinge on one hiring class.
- **Automating all 19 eligible work types loses $141K:** setup fees on 17
  low-volume types outweigh the hours saved.
- **Matching staff to the Monday peak saves $10K and 96 uncovered hours,** the
  most any day-level schedule can do; the rest are within-day peaks.
- **Digitizing paper ahead of demand doesn't pay on retrieval time** (about a
  39-year payback), because few paper charts are ever requested twice.
- **A central records archive saves nothing on today's roster;** about 2 Records
  Specialists only by not backfilling leavers. It adds 1–2 delivery days to each
  paper chart, and the archive move isn't modelled.

The thread running through most of these: **a saving in required hours is only a
saving in money where it cancels an overtime hour or a hiring class.** A freed
half-hour inside somebody's existing paid week costs the same as not freeing it.

## How it is checked

899 tests across 25 files: 898 passing, and 1 that fails on purpose and is
described under the palette above. Every validation check in the
specification is a test, and a session's work is not finished until they pass.

A 26th file, `tests/test_live_colours.py`, holds 45 more that drive a real
browser: they switch the theme through Streamlit's own menu with no refresh and
read back the colours actually painted; they check every card on every run
against what the model says that measure did, card by card, rather than asking
only whether a colour appears on the page somewhere; and they measure the
layout, since a number that covers its own change line is not something a
stylesheet can be read to rule out. Since 24 November they also read back every
coloured word, both download buttons and both banners in each palette and
across a switch, and they measure the scroll position after a run is picked —
three of the fixes that day were only visible in a browser, including a
stylesheet that silently never arrived and a scroll that ran once per session
and then stopped. Since 25 November they also read the angle off every axis
and legend label at both widths, which is the only place the rotation Siri
found could be seen: the spec asked for nothing and Vega-Lite rotated the
labels anyway. They also measure the pixels between each table and its
download buttons, at both widths and on a custom run — which is how the gap
under the detail table was found to be exactly zero — and they read back every
notice as painted, in both palettes and in the sidebar, where the wash sits
over the panel colour rather than over the page. They need playwright, which
is
deliberately not in `requirements.txt`, so they skip themselves when it is
absent — the file says how to run them. They exist because every other test
here asks Python what colour something is, and the bug they were written for
was that Python's answer stopped being true.

- **Hand calculations, against workbooks built by hand first.** The reference
  cases were worked out in Excel before the code existed and are committed
  here: Erlang C in
  [docs/validation/erlang_hand_check.xlsx](docs/validation/erlang_hand_check.xlsx)
  and a four-week backlog rolled forward in
  [docs/validation/backlog_hand_roll.xlsx](docs/validation/backlog_hand_roll.xlsx).
  The tests read those files and fail if the constants in the test and the
  cells in the workbook ever drift apart, so the code has to agree with the
  arithmetic rather than with itself.
- **Tie-outs.** Every value in the workbook is checked against the model's own
  figure to the cent, cell by cell rather than by sample, and every live Excel
  formula is parsed and evaluated against the values the workbook holds. Where
  two tabs reach the same number by different routes, both are checked to
  agree, with neither allowed to be the reference.
- **Pinned headline figures.** A small regression file holds a handful of
  whole-model numbers, so a refactor that quietly moves one cannot pass
  unnoticed. It is meant to fail when an assumption changes — and then the
  number is updated with the reason.
- **Guards against tests that prove nothing.** A test that could pass whether
  or not the thing it measures actually varies is a test that will eventually
  mislead, so the suite asserts the variation too: that a weighted average
  really does differ from a plain one, that a plan really does have short weeks
  in it, that a sensitivity really does move the answer. Each bug found during
  the build was proven the same way — by reverting the fix and confirming that
  the test covering it fails.
- **Calibration against the generated history.** Where an assumption and the
  history disagree, the assumption is wrong. The paper archive was re-sized
  mid-build for exactly this reason: the original figures implied a falling
  non-digital share, and the generated history shows a flat one.

## Limitations

- **A weekly grain cannot see within-day aging,** so a one-day goal is checked
  as days of inventory rather than true response time.
- **Schedules are modelled by day;** there are no intraday shift start times,
  and about 324 of the baseline's 420 uncovered hours sit inside within-day
  peaks.
- **The one-time cost of moving the paper archive to a central site is not
  modelled** — no boxes, trucks, re-indexing or running at two addresses — so
  that scenario's case is an upper bound.
- **A hiring class is sized to the current gap,** rounded up to whole people. A
  smaller gap that recurs can therefore buy more hires than a larger one-off
  gap, so total hires do not follow required hours in a straight line.
- **Every default is illustrative.** Handle times, shrinkage, pay rates,
  automation fees and error rates are plausible placeholders, not benchmarks.
  The model is a structure for asking questions, and the answers move with the
  inputs.

## Logged as future builds

Each of these is recorded in the specification with the reason it was deferred,
rather than left as a silent gap:

- **The proof-of-concept gate** judged on a pooled 12-week error rate with a
  minimum sample size, restoring the full QA sample after any failed week. The
  gate as built tests the sample size as much as the machine.
- **Hiring classes sized to the gap projected over the lead time,** rather than
  the gap at the moment the trigger fires.
- **Vacation smoothing:** the baseline hires permanent people to cover a summer
  gap while two teams are in surplus earlier in the year. Shifting planned
  vacation into the spring surplus is worth comparing against bridging the
  summer with overtime.
- **Intraday shift start times,** so staggered starts can be tested against the
  morning call peak where most of the remaining uncovered hours are.
- **The one-time archive move cost,** which would turn the central-archive
  scenario from an upper bound into a decision.
- **An interactive dashboard** with filters by site and role and a control for
  every scenario input — the next session's work, along with the choice of
  framework.

## Inputs and layout

Every input lives in YAML. No numbers are hard-coded in the logic.

| File | Holds |
|---|---|
| `assumptions.yaml` | Calendar, random seed, demand, handle times, service goals, supply, costs, automation |
| `sites.yaml` | Clusters, sites, size factors, the site-to-site travel table |
| `skills.yaml` | Pools, roles, which role may work which request type |
| `scenarios/` | One overrides file per scenario, with the reasoning for each in comments |

```
src/capacity_model/   the model, one module per area of the spec
app/                  the Streamlit dashboard
app/data/             saved scenario results — generated, and committed
tests/                the validation checks
docs/                 the specification
data/synthetic/       generated data — regenerated, not committed
outputs/              workbook and charts — regenerated, not committed
```
