# Capacity Model (synthetic)

A 52-week workforce capacity-planning model for **Northbrook Records Services**,
a **fictional** six-site medical-records request operation. Written in Python.

Siri L. (GitHub: Sclentzie) is the architect: she designed the model and made
the modelling decisions recorded in the specification, which she drafted with
Claude as a planning partner, and reviewed every checkpoint.
[Claude Code](https://claude.com/claude-code) was the builder, working to that
specification one task at a time. The design document —
[docs/Capacity_Model_Spec.md](docs/Capacity_Model_Spec.md) — is the source of
truth for every input, formula, default and validation check, and records each
decision with its date.

## Everything here is synthetic

Every number in this repository is either an assumption typed into a YAML file
or data **generated by this code** from a fixed random seed. There is no real
company, patient or employee data in it, and none is ever fetched. Run it twice
and you get the same answers.

The operation is invented. The healthcare setting is a modelling scenario and
does not represent any real organization's process. Every default is an
**illustrative starting assumption, not an industry benchmark**.

## What it does

**Demand and forecast.** One driver — records requests per site per week — runs
through 156 weeks of generated history with trend, seasonality, holidays and
noise. Two forecasting methods are fitted and scored against each other on a
13-week holdout they never see: classical decomposition (seasonal index, linear
trend on the de-seasonalised series) and Holt-Winters as the challenger. The
model reports the error for both and uses the better one. Holidays are known
years ahead, so their effect is divided out before fitting and multiplied back
on by date.

**Workload.** Requests become work through 24 work types across five stages, each
measured per request or per chart — a bulk payer audit is ten charts, so it
multiplies retrieval without multiplying intake — and each carrying a lag that
places its hours in the week the work actually lands. Live work at the counter
and on the phones is solved with **Erlang C** at half-hour intervals against two
service goals (80% of calls in 20 seconds, 90% of walk-ins within 10 minutes),
with an 85% occupancy cap. Back-office work is a
**backlog**: each queue carries what the week before left, and is measured in days
of inventory against its stage goal and the 5-day overall goal.

**Supply.** A weekly ledger per role and site tracks starting headcount, hires,
attrition, the training curve, shrinkage and the productive hours that survive
it. Headcount stays fractional — attrition is a weekly rate applied to a
headcount, not a list of named leavers — and no person-level identifiers are
stored anywhere.

**Coverage and hiring.** Where a week is short, the model tries the cheapest
option first: borrow from a nearby site — the round trip comes off the lending
site's hours and the mileage is charged at the set rate — then authorise
overtime against a cap, then accept the gap. Each of those is written to an
event log with
the fields a real coverage log would carry, including a suggested cause for a
person to confirm. A role that stays more than 1 FTE short for three
consecutive weeks triggers a hiring class, sized to the gap and rounded up to
whole people, with a hire-by date counted back through requisition, onboarding
and ramp.

**Automation and human-in-the-loop.** Two halves, kept separate because they
behave differently. *Deflection* removes contacts before they arrive, which
leaves a harder mix behind — calculated, not assumed. *Automation* lets a
machine do work that still arrives, and the work comes back: exceptions, a QA
sample, and legal sign-off where the law requires a person. The human cost a
machine displaces is priced on the **easy items it actually takes**, not an
average item, and the machine's own invoice — per-item fee, setup spread over a
year, one shared platform fee — is counted alongside the labour it saves.

**Scenarios.** 21 runs sit side by side: volume and attrition shocks, pooled
phones, service-goal changes, scheduling shapes, five automation variants, a
central records archive, coordinated digitization, and combinations. No scenario
re-tunes its roster, so each one reports what the change costs the operation it
actually has.

**The workbook.** One Excel file a leader can open without Python, with the ten
tabs the specification names: a curated Summary, all 21 scenarios, the plan and
the supply ledger week by week, the automation ranking, the coverage log, the
non-digital tracker, the hiring plan, the forecast scoreboard with its chart,
and every input used for the run with the YAML key that sets it. The model
writes the measures as values, so they tie to the cent; Excel computes the
totals and the differences as live formulas, so nothing is calculated twice in
two languages.

## Run it (Windows, PowerShell)

```powershell
py -3.14 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
$env:PYTHONPATH = "src"

# All 21 scenarios, the forecast chart, and the workbook (about eight minutes)
.venv\Scripts\python -m capacity_model.export
```

That one command writes `outputs/capacity_model_workbook_SYNTHETIC.xlsx` with
all ten tabs filled, chart included: the Forecast tab draws its own chart when
`outputs/` does not already hold one, which on a fresh clone it does not,
because generated files are not committed. Every stage can also be run alone
— `generate_data`, `forecast`, `work_volume`, `intervals`, `backlog`, `plan`,
`scenarios` — each writing its own CSVs and charts.

Library versions are pinned exactly in `requirements.txt`. A fixed seed only
reproduces the same answers on the same arithmetic, so the versions the checks
were run on are part of the model, not an installation detail.

```powershell
# The validation checks: 656 tests, about 45-50 minutes
.venv\Scripts\python -m pytest
```

One of them skips on a fresh clone: it compares the generated data on disk
against a fresh run, to catch a stale file left behind after an assumption
changed, so it has nothing to compare until you have run `generate_data`.

## What the model found

These are the findings the Summary tab carries, unchanged:

- **A 15% volume rise is the biggest risk in the plan:** +$1.06M, and turnaround
  misses the 5-day goal in 27 weeks, as overtime and undone work absorb the
  rise.
- **Pooling the phones is the largest saving, and it fixes the counter:** one
  pooled phone queue cuts uncovered hours from 420 to 21, while both service
  levels stay above goal.
- **Answering 40 seconds slower saves only about 1 FTE,** because the blended
  counter-and-phone team is staffed to be available, not busy.
- **Automating only the two work types that pay back after setup fees saves
  about $14K,** less than one hiring class, so treat it as break-even. It saves
  hours while the remaining work gets less than about 3% harder; the dollars
  hinge on one hiring class.
- **Automating all 19 eligible work types loses $141K:** setup fees on 17
  low-volume types outweigh the hours saved.
- **Matching staff to the Monday peak saves $10K and 96 uncovered hours,** the
  most any day-level schedule can do; the rest are within-day peaks.
- **Digitizing paper ahead of demand doesn't pay on retrieval time** (about a
  39-year payback), because few paper charts are ever requested twice.
- **A central records archive saves nothing on today's roster;** about 2 Records
  Specialists only by not backfilling leavers. It adds 1–2 delivery days to each
  paper chart, and the archive move isn't modelled.

The thread running through most of these: **a saving in required hours is only a
saving in money where it cancels an overtime hour or a hiring class.** A freed
half-hour inside somebody's existing paid week costs the same as not freeing it.

## How it is checked

656 tests across 21 files, all passing. Every validation check in the
specification is a test, and a session's work is not finished until they pass.

- **Hand calculations, against workbooks built by hand first.** The reference
  cases were worked out in Excel before the code existed and are committed
  here: Erlang C in
  [docs/validation/erlang_hand_check.xlsx](docs/validation/erlang_hand_check.xlsx)
  and a four-week backlog rolled forward in
  [docs/validation/backlog_hand_roll.xlsx](docs/validation/backlog_hand_roll.xlsx).
  The tests read those files and fail if the constants in the test and the
  cells in the workbook ever drift apart, so the code has to agree with the
  arithmetic rather than with itself.
- **Tie-outs.** Every value in the workbook is checked against the model's own
  figure to the cent, cell by cell rather than by sample, and every live Excel
  formula is parsed and evaluated against the values the workbook holds. Where
  two tabs reach the same number by different routes, both are checked to
  agree, with neither allowed to be the reference.
- **Pinned headline figures.** A small regression file holds a handful of
  whole-model numbers, so a refactor that quietly moves one cannot pass
  unnoticed. It is meant to fail when an assumption changes — and then the
  number is updated with the reason.
- **Guards against tests that prove nothing.** A test that could pass whether
  or not the thing it measures actually varies is a test that will eventually
  mislead, so the suite asserts the variation too: that a weighted average
  really does differ from a plain one, that a plan really does have short weeks
  in it, that a sensitivity really does move the answer. Each bug found during
  the build was proven the same way — by reverting the fix and confirming that
  the test covering it fails.
- **Calibration against the generated history.** Where an assumption and the
  history disagree, the assumption is wrong. The paper archive was re-sized
  mid-build for exactly this reason: the original figures implied a falling
  non-digital share, and the generated history shows a flat one.

## Limitations

- **A weekly grain cannot see within-day aging,** so a one-day goal is checked
  as days of inventory rather than true response time.
- **Schedules are modelled by day;** there are no intraday shift start times,
  and about 324 of the baseline's 420 uncovered hours sit inside within-day
  peaks.
- **The one-time cost of moving the paper archive to a central site is not
  modelled** — no boxes, trucks, re-indexing or running at two addresses — so
  that scenario's case is an upper bound.
- **A hiring class is sized to the current gap,** rounded up to whole people. A
  smaller gap that recurs can therefore buy more hires than a larger one-off
  gap, so total hires do not follow required hours in a straight line.
- **Every default is illustrative.** Handle times, shrinkage, pay rates,
  automation fees and error rates are plausible placeholders, not benchmarks.
  The model is a structure for asking questions, and the answers move with the
  inputs.

## Logged as future builds

Each of these is recorded in the specification with the reason it was deferred,
rather than left as a silent gap:

- **The proof-of-concept gate** judged on a pooled 12-week error rate with a
  minimum sample size, restoring the full QA sample after any failed week. The
  gate as built tests the sample size as much as the machine.
- **Hiring classes sized to the gap projected over the lead time,** rather than
  the gap at the moment the trigger fires.
- **Vacation smoothing:** the baseline hires permanent people to cover a summer
  gap while two teams are in surplus earlier in the year. Shifting planned
  vacation into the spring surplus is worth comparing against bridging the
  summer with overtime.
- **Intraday shift start times,** so staggered starts can be tested against the
  morning call peak where most of the remaining uncovered hours are.
- **The one-time archive move cost,** which would turn the central-archive
  scenario from an upper bound into a decision.
- **An interactive dashboard** with filters by site and role and a control for
  every scenario input — the next session's work, along with the choice of
  framework.

## Inputs and layout

Every input lives in YAML. No numbers are hard-coded in the logic.

| File | Holds |
|---|---|
| `assumptions.yaml` | Calendar, random seed, demand, handle times, service goals, supply, costs, automation |
| `sites.yaml` | Clusters, sites, size factors, the site-to-site travel table |
| `skills.yaml` | Pools, roles, which role may work which request type |
| `scenarios/` | One overrides file per scenario, with the reasoning for each in comments |

```
src/capacity_model/   the model, one module per area of the spec
tests/                the validation checks
docs/                 the specification
data/synthetic/       generated data — regenerated, not committed
outputs/              workbook and charts — regenerated, not committed
```
